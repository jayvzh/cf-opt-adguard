# AI 协作项目开发文档规范标准（参考样板）

> 版本：v1.0 ｜ 性质：跨项目共享的参考规范，非某个项目的业务文档
> 来源：从 AbulmShelf 项目的三层文档实践提炼，经 DanmuTV 项目完整落地重构后补充实战教训
> 用法：新项目按本规范搭建文档；存量项目按 §8 步骤迁移；§9 是真实踩坑记录，迁移前必读

---

## 1. 目的与适用范围

### 1.1 解决什么问题
AI IDE（Trae / Cursor 等）参与开发时，文档同时服务两类读者：
- **AI**：上下文有限、会无目标全局扫描浪费 token、容易超范围改动、看不到隐式约定；
- **人**：需要快速判断需求边界、审查架构、对外共享项目。

没有规范时的典型病症：文档散落且重复、规则多处维护导致互相漂移、AI 每次重复试错、接口契约口头约定、踩过的坑再踩一遍。

### 1.2 适用范围
- 有明确代码仓库、由 AI IDE 持续参与开发的项目（不限语言/栈）；
- 单体或中型以下代码库（数万行以内）；大型 monorepo 可按子包各套一份。

### 1.3 核心设计理念
1. **分层加载**：日常任务只读一页精简规则；架构/范围判断才打开完整文档。按任务点开，禁止整目录通读。
2. **单一事实源**：每个事实只在一处权威维护，其他地方只放指针。
3. **代码是最终事实**：文档描述现状时必须从代码核实，不凭记忆/spec/注释转述。
4. **只写项目独有知识**：官方文档和通用编程常识不写。

## 2. 三层文档体系总览

```
项目根/
├── 开发规则.md              ← 第 1 层：精简规则（AI 的第一份规则，日常只看它）
├── README.md                ← 对外入口：部署说明 + 项目文档索引表
├── docs/                    ← 第 2 层：主题文档（按任务点开，git 管理）
│   ├── PRD.md                  产品需求（做什么/不做什么）
│   ├── ARCHITECTURE.md         技术架构与运行机制
│   ├── PROJECT_STRUCTURE.md    目录职责与模块边界
│   ├── DATA_MODEL.md           数据结构/表/配置项
│   ├── API.md                  接口契约（唯一契约来源）
│   ├── UI_DESIGN.md            界面与交互（有前端时）
│   ├── DEVELOPMENT_RULES.md    完整开发总则 + 交付自检清单
│   ├── context.md              知识四件套：背景与现状
│   ├── decisions.md                     选型决策记录
│   ├── pitfalls.md                      踩坑与绕开姿势
│   ├── conventions.md                   项目专属约定与技术债
│   ├── CONTRIBUTING.md         本地开发/构建/部署细节（可选）
│   └── <专题>.md               引擎/算法等专题（按需，如 SORT_ENGINE.md）
└── .trae/rules/
 │   └── 开发规则.md           ← 第 3 层：指针（3 行 + 可选 1 行最高频禁令，被 IDE 自动注入）
```

| 层 | 文件 | 读者触发时机 | 篇幅 |
| --- | --- | --- | --- |
| L1 | 根 `开发规则.md` | 每次日常任务 | 一屏内（约 50~80 行） |
| L2 | `docs/*.md` | 文档地图按任务指向时 | 单主题，一般 <400 行 |
| L3 | `.trae/rules/开发规则.md` | IDE 每次对话自动注入 | 3~4 行 |
| 入口 | `README.md` 文档索引 | 新人/外部用户 | 随项目 |

**为什么是三份规则而不是一份**：L3 每次对话注入全文会浪费 token 且容易被忽略；L2 完整总则太长不适合日常读；L1 是两者之间"一屏可执行"的折中。三份之间是**指针关系，不是复制关系**。

## 3. 各层标准

### 3.1 L3：`.trae/rules/开发规则.md` —— 指针（默认三行，最多四行）

固定格式，做三件事：指路、给宗旨、给环境命令。

```markdown
每次开始一项中型任务时，请阅读并遵守根目录下的 开发规则.md（完整总则：docs/DEVELOPMENT_RULES.md）。
宗旨：先查文档、少扫描、小步改、多复用、不超范围。
<语言> 环境使用 <环境管理器> <环境名>；开发环境用 ./dev.sh start|stop|restart|status|logs。
<可选第四行，仅限最高频一条> 如：禁止为小改动、找元素、确认元素存在而开浏览器/截图；验证先读代码+构建+curl，只有纯视觉布局问题或用户明确要求时才最多截一张。
```

规则：
- **禁止**在此写红线清单、自检表等实质内容（它们的归处在 L1/L2）。
- **唯一例外**：可追加**一行**项目最高频、最易复发的浪费行为禁令（实测"禁止为小改动/找元素开浏览器截图"值得占用这一行，因为 L3 每次对话自动注入，是拦截高频坏习惯最有效的位置）；只能一行，不得膨胀成第二条清单。
- 该目录通常被 `.gitignore` 忽略（见 §9 教训 1），所以**它不是知识的权威存放处**，丢失后按本模板可秒重建。
- 若 IDE 支持多个规则文件，也只放这一个指针文件，不要复活"补充规则"（见 §9 教训 2）。

### 3.2 L1：根目录 `开发规则.md` —— 精简版

固定六段结构：

```markdown
# <项目名> 开发规则（精简版 v1.0）

> 给 AI 的第一份规则。日常任务先执行本页即可，能省 token 就不必打开完整总则。
> 完整总则：docs/DEVELOPMENT_RULES.md（架构、范围判断、完整自检时读；冲突以它为准）。
> 宗旨：先查文档、少扫描、小步改、不超范围。

## 0. 项目一句话
<技术栈一句话> + <业务一句话>，含关键环境（如 conda 环境名）。

## 1. 文档地图（按任务点开对应文档，禁止整目录通读）
| 任务 | 打开 |
| --- | --- |
| 判定需求范围/非目标 | docs/PRD.md |
| 架构/核心机制 | docs/ARCHITECTURE.md |
| ……（按项目实际列全） | |

## 2. 铁律（永久生效，违反即返工）
- 5~8 条，每条可机械判定（"禁止 X""必须走 Y"），不写倡导性废话。
- 必含一条**验证手段红线**（实测最常被违反）：禁止默认开浏览器/截图；找元素用 Grep/Read；验证按"读代码 ＞ 构建/冒烟 ＞ 接口 curl ＞ 浏览器"逐级进行；浏览器截图仅限纯视觉布局问题或用户明确要求，且每次最多一张关键态。

## 3. 省 token 的行为约束
- 先查文档再动手；检索限定目录；大文件分段读；小 diff；不臆造；结论先行。
- 验证手段红线的展开说明放 §2 铁律，此处只放一句指针，不重复第二份。

## 4. 常用命令（免翻脚本）
- 开发启停、冒烟、构建、鉴权自检；每条必须实跑核实过（见 §9 教训 6）。

## 5. 交付自检（10 秒）
- 4~6 个问句覆盖最高频事故；必须包含一问："有没有为小改动/找元素开浏览器截图？截图是否在白名单内且只有一张？"；末行指向完整清单：docs/DEVELOPMENT_RULES.md §10。
```

要求：
- 控制在一屏；写不下说明内容该下沉到 L2。
- 铁律要与 L2 总则 §红线 **同义不重复展开**，L1 写"是什么"，L2 可写"为什么/怎么查"。

### 3.3 L2：`docs/` 主题文档

#### 3.3.1 必选文档与职责边界（越界 = 重复的根源）

| 文档 | 只回答 | 禁止写 |
| --- | --- | --- |
| PRD.md | 做什么、为谁做、不做什么（非目标）、业务规则 | 技术实现、表结构 |
| ARCHITECTURE.md | 分层依赖、运行机制、关键状态机/调度、鉴权 | 需求背景、逐文件说明 |
| PROJECT_STRUCTURE.md | 目录/模块职责与边界、核心数据流 | 接口字段、建表 DDL |
| DATA_MODEL.md | 表/字段/索引、迁移约定、配置项全集 | 接口 HTTP 细节 |
| API.md | 端点、参数、响应、错误码、契约特例 | 内部实现、页面交互 |
| UI_DESIGN.md | 页面结构、区块、交互状态约定 | 接口实现 |
| DEVELOPMENT_RULES.md | 环境、红线、分层约束、业务数值护栏、验证、自检 | 需求和架构的重复描述 |

边界判断口诀：**"做什么"→PRD；"怎么跑"→ARCHITECTURE；"放哪"→STRUCTURE；"存什么"→DATA_MODEL；"怎么调"→API；"怎么看"→UI；"怎么干活"→RULES。**

#### 3.3.2 知识四件套（轻量、持续追加）

| 文档 | 收录标准 | 格式 |
| --- | --- | --- |
| context.md | 背景与现状（会变化、有时效性） | 背景/现状 + 文档导航表 |
| decisions.md | 重要、非显而易见、未来可能复用的选型（ADR） | 日期/标题/背景/决策/原因/影响 |
| pitfalls.md | 非显而易见、可能再踩的坑 | 现象/原因/解决/备注 |
| conventions.md | 项目专属约定、缩写、目录放置理由、技术债绕法 | 分主题条目 |

去重原则：
- context.md **只写"这是什么项目、到哪一步"**，架构机制一句带过 + 链接，不复述 ARCHITECTURE；
- 四件套之间用链接互引（pitfall 指向相关 decision），不复制内容；
- 通用知识（"什么是 WAL""JWT 原理"）一律不写。

#### 3.3.3 文档头注模板（每篇 L2 文档必备）

```markdown
# <主题全称>（<英文文件名>）

> 版本：v1.0 ｜ 一句话说明本文职责与边界。
> 相关：<上游文档> 见 [X.md](X.md)，<下游> 见 [Y.md](Y.md)。
> 更新时机：<什么代码变更时必须改本文>。
```

#### 3.3.4 可选文档
- `CONTRIBUTING.md`：开源协作、ffmpeg/二进制等特殊构建步骤；
- `<ENGINE>_ENGINE.md`：复杂算法/协议专题（参考 AbulmShelf 的 SORT_ENGINE.md）；
- `SPRINT_PLAN.md` / `SPRINTn_TASK.md`：阶段化开发时，**一次只给 AI 一个 Sprint 任务书**。

### 3.4 README —— 对外入口
部署说明面向使用者；文末放"项目文档"索引表（两列：文档 | 内容），把 L1 + 全部 L2 登记一遍。这是外部世界发现文档的唯一入口，新增 docs 文件必须回写此表。

## 4. 编写原则

1. **从代码取证，不臆造**。写 API 字段、配置项、命令、业务数值前先读代码；spec 和注释只能当线索，与代码冲突时以代码为准，并在 pitfalls 记录差异（案例见 §9 教训 5）。
2. **单一事实源**。契约只在 API.md、表只在 DATA_MODEL.md、红线只在 RULES；他处一律链接，禁止复制第三份。
3. **去重后互补**。两文档内容重叠时，选定唯一归处，另一处删内容留链接。
4. **文档地图驱动**。L1 的地图表是 AI 的路由表，任务→文档一一对应，避免整目录通读。
5. **命令必须可执行**。文档里的脚本名、参数、端口、环境名以脚本/配置实际为准。
6. **可机械判定的规则**。"分层只准向下""禁直接 fetch"优于"注意代码质量"。
7. **短而具体**。pitfall/decision 附现象/原因/做法；不灌水、不贴官方文档。
8. **中文项目可用中文文件名**（`开发规则.md`），但需知道 git 转义显示问题（§9 教训 7）。

---

## 5. 交叉引用规范

1. 同目录文档用相对链接：`[API.md](API.md)`；引用代码：`[routes.py](../backend/app/api/routes.py)`。
2. **章节引用优先用标题文字而非编号**：写"见《交付自检》一节"比"见 §10"抗漂移；确需用编号时，增删章节后全文复查。
3. **删除/重命名任何文档前，全仓搜索旧名**（含 .md 内引用、README 索引、规则文件），一次性改完。
4. 每次新增 docs 文件，三处登记：L1 文档地图、README 索引、context 导航（如适用）。

## 6. 维护机制

### 6.1 代码变更 → 文档同步映射（写进 DEVELOPMENT_RULES §文档维护）
| 代码变更 | 必须同步 |
| --- | --- |
| 接口/响应/错误码 | API.md（双端同时改） |
| 表结构/配置项 | DATA_MODEL.md |
| 架构/目录/运行方式 | ARCHITECTURE.md / PROJECT_STRUCTURE.md / context.md |
| 页面交互 | UI_DESIGN.md |
| 重要选型 | decisions.md |
| 踩坑 | pitfalls.md |
| 新约定/发现技术债 | conventions.md |

### 6.2 生命周期规则
- 表结构/接口契约变更：迁移只增不改等护栏写进 DATA_MODEL/RULES；
- 完成一个 task 立即勾选任务清单，不攒到最后；
- 文档随代码同一变更交付，不接受"以后补文档"。

## 7. 文档质量验收清单（迁移/新建完成后逐项过）

- [ ] 三层齐备：L1 一屏内、L3 仅 3 行指针、L2 主题文档职责不越界
- [ ] L1 文档地图覆盖全部 L2 文件，链接全部可达
- [ ] 每个事实只有一个权威归处，重复内容已删改为链接
- [ ] API/配置/命令/数值均与代码核对一致（抽查 3 处以上）
- [ ] README 文档索引登记全部文档
- [ ] 全文搜索无悬空引用、无失效章节号
- [ ] 权威文档均在 git 管理路径内（.trae 等被忽略目录只放指针）
- [ ] pitfalls/conventions 写的是项目独有知识，无通用常识
- [ ] 头注三要素齐全：职责边界、相关文档、更新时机
- [ ] 浏览器/截图约束四处一致：L3 一行禁令（可选）、L1 铁律 + 自检一问、L2 红线展开 + 自检清单项，且白名单口径相同

## 8. 落地指南

### 8.1 新项目（约 0.5~1 天）
1. 建骨架：按 §2 目录树建空文件，先写 L3 三行指针；
2. 写 PRD（含非目标）→ PROJECT_STRUCTURE（空架子也先定边界）；
3. 随首个里程碑补 ARCHITECTURE / DATA_MODEL / API / UI，禁止事后补全套；
4. 写 L1 精简规则（地图 + 铁律直接从前四篇提炼）；
5. 写 DEVELOPMENT_RULES（环境、红线、验证、自检）；
6. README 加索引；四件套从第一条真实决策/坑开始养。

### 8.2 存量项目重构（本次验证过的顺序）
1. **先读代码和现有材料取证**：spec、设计稿、路由、模型、配置、入口脚本；
2. 大文件（>1500 行）用关键词检索 + 分段读，可用搜索子代理做结构化摘要，不通读；
3. 按职责边界起草 L2 各篇，字段/命令逐项与代码核对；
4. 建 L1，地图指向 L2；L3 改指针；README 加索引；
5. 四件套去重：context 只留背景现状，重复的架构内容删改链接；
6. 全仓核查：链接可达、无悬空引用、章节号正确；
7. 按 §7 验收清单收尾。

## 9. 实战教训（DanmuTV 重构真实案例，迁移前必读）

1. **被 .gitignore 的目录不能放权威内容。** `.trae/` 被忽略，最初把"交付自检清单"放在 `.trae/rules/开发补充规则.md`，它不入库、无法 review、换机器即丢。
   → 对策：权威内容只放 git 管理的 `docs/`；`.trae/` 只留可秒重建的三行指针。
2. **规则文件最多两份 + 一个指针，杜绝"补充规则"。** 曾同时存在根规则、docs 总则、.trae 规则、.trae 补充规则四份，红线与自检多处复制，必然漂移。
   → 对策：删除补充文件，11 项自检并入 docs 总则固定章节（§10），其他位置只留链接；并写明"精简版与总则冲突以总则为准"。
3. **删文档必然产生悬空引用。** 删除补充规则后，根规则和总则文首/标题共 3 处仍引用它。
   → 对策：删除前 `grep -r 文件名`；删后再搜一遍确认零结果；引用与被引文件在同一变更内修改。
4. **章节号引用会错位。** L1 写"详见 §9"，而总则自检实际是 §10（中间新增过章节）。
   → 对策：优先按标题文字引用；用编号则增删章节后全文复查。
5. **spec / 代码注释可能与实现不符，文档必须以代码为准。** spec 与函数注释都称"历史详情只保留最近 20 条"，实际代码只裁剪概要到 100 条、details 从不裁剪（20 只是分页默认值）。
   → 对策：文档按代码现状描述，差异记入 pitfalls.md（现象/原因/解决/备注），不照抄 spec。
6. **文档里的命令会与脚本漂移。** 文档写 `./dev.sh [all|backend|frontend]`，脚本根本不接受 `all`。
   → 对策：命令类内容以 `--help`/脚本源码为准实跑核实；脚本改参数时同步改 L1、docs 总则、CONTRIBUTING 三处。
7. **中文文件名在 git 输出中被转义，容易误判"文件没生效"。** `git status` 把 `开发规则.md` 显示成八进制转义串，一度以为新文件未被追踪。
   → 对策：用 `git -c core.quotepath=false status` 或 `git ls-files | grep` 确认；不影响实际使用。
8. **现状类文档与架构文档最容易重复。** context.md 原含一整段架构描述，与 ARCHITECTURE.md 重叠。
   → 对策：context 只留"定位 + 现状 + 文档导航"，架构一句带过并链接。
9. **大段重构先定范围再动手。** 通过一次性确认三个决策（对标完整度、四件套去留、规则文件形态），避免过度产出和返工。范围不明时先问，不批量生成。
10. **软建议拦不住坏习惯，"少截图"必须升级为红线且多点设防。** 第一次只在省 token 段写了句"UI 验证少截图"，结果小改动截图、找个元素也开浏览器——埋在建议区的约束 AI 根本不遵守；浏览器截图单张极耗 token，逐页面/逐状态连环截图会迅速吃掉预算，而找元素、确认存在、验证逻辑/绑定/接口/路由，用 Grep/Read、`npm run build`、curl 即可判定。
    → 对策（四处一致才到位）：
    - L3 指针：利用"每次对话自动注入"的特性，加**一行**硬禁令（禁止为小改动/找元素开浏览器截图）；
    - L1 铁律段：写成可机械判定的红线 + 验证升级阶梯（读代码 ＞ 构建/冒烟 ＞ curl ＞ 浏览器，上一级能证明就不做下一级）+ 白名单（仅纯视觉布局问题或用户明确要求，每次≤1 张）；
    - L2 总则红线节：展开同一条；自检清单（§10）加对应勾选项；
    - 白名单只有两个口子：纯视觉/布局/CSS 且静态无法判断、用户明确要求；其余一律不开浏览器。

## 10. 最小模板速查

**L3 指针**：见 §3.1，三行（指路/宗旨/环境）；可选第四行：项目最高频浪费行为的一行硬禁令（如禁止为小改动开浏览器截图）。

**L1 骨架**：见 §3.2 代码块，六段：一句话 / 文档地图 / 铁律（含验证手段红线） / 省 token / 常用命令 / 10 秒自检（含截图一问）。

**L2 头注**：见 §3.3.3。

**四件套条目格式**：
- decision：日期 + 标题 + 背景/决策/原因/影响；
- pitfall：标题 + 现象/原因/解决/备注；
- convention：分"目录与模块 / 命名与缩写 / 技术债与绕法"三组。
